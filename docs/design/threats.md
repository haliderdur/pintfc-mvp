# Threats and controls

| # | Misuse | Control |
|---|---|---|
| T1 | A visitor (or anyone) uses the public Supabase anon key — visible in any Next.js client bundle — to query base tables (`players`, `rsvps`, `player_stat_lines`, …) directly over Supabase's REST/GraphQL API, bypassing the app entirely. | RLS default-deny on every base table; only the public-safe views (`public_players`, `public_profile`, `public_rsvp_counts`, published-only results) are readable by the `anon`/`authenticated` roles. Verified by database-level tests that query the base tables with the anon key and expect zero rows / a permission error. |
| T2 | A signed-in player submits an RSVP after the match's cutoff by calling the API or Supabase REST directly, skipping the disabled UI button. | RLS policy on `rsvps` INSERT/UPDATE requires `now() < matches.rsvp_cutoff_at` (`rules.md` §1). The Route Handler also checks this for a clean error, but the policy is what actually blocks it — tested by attempting a direct Supabase write with a valid player JWT after the cutoff. |
| T3 | A signed-in player writes an RSVP row for a teammate (`player_id` not their own). | RLS policy requires `player_id = (select id from players where auth_user_id = auth.uid())`. Tested with one player's JWT attempting to insert/update another player's `rsvps` row. |
| T4 | A client reads a minor player's photo/nationality/stats despite missing guardian consent, by requesting the base `players`/`player_consents` tables instead of `public_profile`. | `public_profile` view bakes in the guardian-consent override (`rules.md` §2); base tables have no anon/authenticated SELECT grant at all. Tested at the database level against both the view (should hide fields) and the base table (should deny access). |
| T5 | "Sign out of all devices" only clears the calling device's cookie, leaving other devices' sessions valid. | Use Supabase Auth's global/`scope: 'global'` sign-out, which revokes refresh tokens server-side, not just a local cookie clear. Tested end-to-end with two authenticated sessions for the same player. |
| T6 | The archived player's data is still reachable through some query path (e.g. a direct profile URL by id). | `public_players`/`public_profile` filter `is_archived = false` at the view level, so `/players/[archived-id]` gets zero rows → renders 404. Not an app-layer `if` that a new code path could forget. |
| T7 | A preview deployment's test writes (RSVPs, consent toggles) pollute the data students see at the live demo, since preview and production share one Supabase project (Decision D4). | Re-run the idempotent `scripts/seed.ts` (truncate + reseed) immediately before any class/demo; avoid exercising writes against the shared project in the hours before a demo. Documented as an operational control, not a code control — tracked as Risk R5-adjacent in `docs/REQUIREMENTS.md`. |
| T8 | Cross-site request forgery on a state-changing endpoint (RSVP submit, privacy PATCH) from a malicious third-party page, using the victim's browser session. | Session cookies are `SameSite=Lax`; Route Handlers only accept same-origin `fetch` calls from the app's own client code (no form-based cross-origin POST is wired up). Accepted as adequately covered by `SameSite=Lax` for this MVP's risk level (fake data, no payments) — revisit if real PII is ever added. |
| T9 | The Supabase service-role key (full DB access, bypasses RLS) leaks into the client bundle or a committed file. | Service-role key is read only by `scripts/seed.ts`, run locally/CI with the key from an untracked `.env.local` / CI secret — never referenced by any file under `app/` or `components/` that ships to the browser. `CLAUDE.md`'s secrets rule covers the "never print/log/commit" half; this is the architectural half. |
| T10 | An under-18 player without guardian consent uses the privacy-settings UI to toggle an opt-in field on, and the server accepts it because only the UI disabled the control. | `PATCH /api/privacy` returns `403 FORBIDDEN_MINOR_CONSENT` for that case server-side (`api.md`), independent of whatever the UI rendered — same consent rule as T4, applied on write instead of read. |
